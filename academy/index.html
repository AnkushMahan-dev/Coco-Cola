Measure, don't assume. Speed-up varies by task, developer, and system access. Pick a handful of representative objects, log the before/after on real tickets, and let your own numbers set expectations. Treat any headline "N× faster" claim as a hypothesis to test, not a fact.

Habits that drive the gains

  1. Give Claude the spec, not a one-liner. Paste the relevant FS section, table/field names, and your naming conventions. Better input → less rework.
  2. Ask for a plan first. Have Claude outline the technical approach before generating code, so you catch design issues early and cheaply.
  3. Iterate in small steps. Generate one artefact (a method, a report block) at a time and review it, rather than one giant program you can't verify.
  4. Always run the checks. Syntax check, ATC, and unit tests in your own system are the source of truth — Claude's output is a strong draft, not an activated object.
  5. Keep a project standards note. A short conventions file (naming, package, clean-ABAP rules) makes every generation consistent without repeating yourself.

Worked Case: Developing an ABAP program from a Functional Specification

A complete, realistic walkthrough — from an FS to an activated, unit-tested report — showing exactly what you hand to Claude at each step and what you do yourself.

The scenario & the Functional Specification

FS-2041 — Open Sales Orders Report. The business wants an ALV report listing open sales order items for a given sales organisation and date range, so the customer-service team can chase overdue deliveries.
FS elementDetail
ObjectiveList open sales order items (not fully delivered) with customer, material, quantity, value and requested delivery date.
Selection screenSales Org (VKORG, mandatory), Requested Delivery Date range (VDATU), Customer (KUNNR, optional).
Source dataHeader VBAK, Items VBAP, Status VBUP (delivery status ≠ fully delivered).
OutputEditable ALV grid: Order, Item, Sold-to, Material, Order Qty, Net Value, Currency, Req. Delivery Date.
RulesExclude fully delivered items (LFSTA = 'C'); sort by delivery date ascending; totals on Net Value.
Non-functionalFollow clean-ABAP naming; no SELECT *; handle "no data found"; must pass ATC.

The workflow, step by step

  1. 1 · Share the FS and ask for a technical design (not code yet)

    Start by having Claude translate the FS into a technical approach you can review. This is the cheapest place to catch a wrong table or a missed rule.

    YOU → CLAUDEHere is Functional Spec FS-2041 (pasted below). Before writing any ABAP, give me a short Technical Specification: the tables and joins, the selection screen, the processing logic as pseudocode, and any risks or open questions. Follow clean-ABAP naming. Do not use SELECT *.

  2. 2 · Review the Technical Specification Claude proposes

    Claude returns a design like the one below. You validate it against the business need and your system before a single line of code exists.

    * Technical Specification — FS-2041 Open Sales Orders (draft)
* Tables : VBAK (header), VBAP (items), VBUP (item status)
* Join   : VBAP-VBELN = VBAK-VBELN
*          VBUP-VBELN = VBAP-VBELN AND VBUP-POSNR = VBAP-POSNR
* Filter : VBAK-VKORG = p_vkorg
*          VBAK-VDATU IN so_vdatu
*          VBAK-KUNNR IN so_kunnr (optional)
*          VBUP-LFSTA <> 'C'  (not fully delivered)
* Output : ALV via CL_SALV_TABLE, sorted by VDATU asc, sum NETWR
* Risks  : large VBAP volumes -> restrict by date; check authorisations (VKORG)
    Ask follow-ups here: "Should we add a VKORG authority-check?" — refining the design now is far cheaper than reworking code later.

  3. 3 · Ask Claude to generate the ABAP program

    With the design agreed, request the code. Be explicit about output type and standards.

    YOU → CLAUDEGood. Now write the ABAP report ZSD_OPEN_ORDERS from that design. Use a single SELECT with an INNER JOIN, CL_SALV_TABLE for output, a mandatory VKORG parameter, and proper SY-SUBRC / no-data handling. Add clean-ABAP style comments.
    REPORT zsd_open_orders.

TYPES: BEGIN OF ty_order,
         vbeln TYPE vbak-vbeln,
         posnr TYPE vbap-posnr,
         kunnr TYPE vbak-kunnr,
         matnr TYPE vbap-matnr,
         kwmeng TYPE vbap-kwmeng,
         netwr TYPE vbap-netwr,
         waerk TYPE vbak-waerk,
         vdatu TYPE vbak-vdatu,
       END OF ty_order.

DATA gt_orders TYPE STANDARD TABLE OF ty_order.

PARAMETERS     p_vkorg TYPE vbak-vkorg OBLIGATORY.
SELECT-OPTIONS: so_vdatu FOR "gv_vdatu, so_kunnr FOR "gv_kunnr.

START-OF-SELECTION.
  SELECT h~vbeln i~posnr h~kunnr i~matnr
         i~kwmeng i~netwr h~waerk h~vdatu
    FROM vbak AS h
    INNER JOIN vbap AS i ON i~vbeln = h~vbeln
    INNER JOIN vbup AS s ON s~vbeln = i~vbeln
                          AND s~posnr = i~posnr
    INTO CORRESPONDING FIELDS OF TABLE @gt_orders
    WHERE h~vkorg  = @p_vkorg
      AND h~vdatu IN @so_vdatu
      AND h~kunnr IN @so_kunnr
      AND s~lfsta <> 'C'.       " exclude fully delivered

  IF sy-subrc <> 0.
    MESSAGE 'No open orders for the given selection' TYPE 'S'.
    RETURN.
  ENDIF.

  SORT gt_orders BY vdatu ASCENDING.

  TRY.
      DATA(lo_alv) = cl_salv_table=>factory(
        IMPORTING r_salv_table = DATA(lr_alv)
        CHANGING  t_table      = gt_orders ).
      lr_alv->display( ).
    CATCH cx_salv_msg INTO DATA(lx_msg).
      MESSAGE lx_msg->get_text( ) TYPE 'E'.
  ENDTRY.
    Your job, not Claude's: paste this into Eclipse ADT / SE80, run a syntax check, adjust field names to your release, and confirm the logic against the FS. The generated code is a strong first draft — you activate it.

  4. 4 · Generate ABAP Unit tests

    Ask for tests so the object ships verified rather than "looked fine when I ran it once".

    YOU → CLAUDEWrite an ABAP Unit test class for the selection logic: one case with open items, one where every item is fully delivered (expect empty result), and one with an invalid VKORG. Use test doubles so it doesn't hit the live tables.

  5. 5 · Self-review against standards, then run ATC

    Before the transport, have Claude sanity-check its own output against your rules, then let ABAP Test Cockpit be the final word in your system.

    YOU → CLAUDEReview ZSD_OPEN_ORDERS against clean-ABAP: naming, no SELECT *, error handling, performance on large VBAP. List anything ATC would likely flag and show the fix.

  6. 6 · Activate, test, document

    Run it in your system, unit-test it, and — if you like — ask Claude to draft the Technical Specification document and change-log from the final code, closing the loop back to the FS.

The pattern to remember: FS → design → code → tests → review → activate. Claude drafts each artefact and explains its reasoning; you validate against the business need and own everything that enters a transport.

Getting Started

A short path from zero to your first FS-to-code task.

  1. 1 · Pick a low-risk first task

    Choose a small report or a routine enhancement you understand well — something you can judge the output on.

  2. 2 · Prepare your inputs

    Have the FS section, the table/field names, and a short note of your team's naming and clean-ABAP conventions ready to paste.

  3. 3 · Ask for a design before code

    Get the technical approach first, review it, then request the ABAP. Iterate one artefact at a time.

  4. 4 · Verify in your own system

    Syntax check, ATC, and ABAP Unit tests are the source of truth. Never activate un-reviewed generated code.

  5. 5 · Capture what works

    Keep a running note of prompts and conventions that give good results, and share it with the team so quality stays consistent.
